# Changelog

Each entry lists what changed. An entry that requires changes to an app's own files (AGENTS.md, TASKS.md, the PRD, `tools/check.cfg`) ends with **Upgrade steps**, which onboarding carries out during an upgrade.

## Unreleased

- **The guard and the Read rules block reads of .env.local and the other .env.<suffix> files.** The settings template now denies the Read tool `.env.local`, `.env.production`, `.env.development`, `.env.staging` and `.env.test`, each in its plain and `**/` form, and `.env.*.local`, which covers the other local variants. The guard hook (`guard-commands.sh`) blocks a shell `cat`, `head`, `tail`, `less`, `more` or `strings` of any `.env.<suffix>` file, quoted or not, and every such file named after one of those commands on the same line (`tail -n 20 .env.local`, `cat .env.example .env.local`). The committed templates `.env.example`, `.env.sample`, `.env.template` and `.env.dist` stay readable, and so does a command that doesn't read the file, such as `ls .env.local`. The Read rules name the common suffixes rather than `.env.*`, because a pattern such as `.env.*` would also deny the templates. Another suffix, such as `.env.custom`, can still be opened with the Read tool; the guard covers it only for a shell read.
  - **Upgrade steps:** the hook and `.claude/settings.json` are framework-owned and arrive with the upgrade (if you edited `.claude/settings.json`, merge its `.satt-new` file). Restart Claude Code so the new deny rules load.

## 0.14.4 (2026-10-30)

- **The guard and the Read rules block reads of .env, .pem and .key files.** The settings template now denies the Read tool `.env`, `**/.env`, `*.pem`, `**/*.pem`, `*.key` and `**/*.key`, and the guard hook (`guard-commands.sh`) blocks a shell `cat`, `head`, `tail`, `less`, `more` or `strings` of such a file, quoted or not, from the current folder or one below it (`cat .env`, `head ./.env`, `cat "certs/server.pem"`, `less deploy.key`, `head '.env'`). A prompt injected from a fetched page could otherwise put a live secret into the conversation, where it has to be treated as compromised and rotated. Names that only look like one pass, such as `.env.example`, `README.md` and `docs/keys.md`. Like the credential-store check, the guard matches the command text, so a read by another command (`grep`, `sed`, a script) isn't caught, and the rules cover `.env` itself, not variants such as `.env.local`.
  - **Upgrade steps:** the hook and `.claude/settings.json` are framework-owned and arrive with the upgrade (if you edited `.claude/settings.json`, merge its `.satt-new` file). Restart Claude Code so the new deny rules load.

## 0.14.3 (2026-10-30)

- **The guard closes the git grep pager and the credential stores, and the pre-commit hook scans every commit for secrets.** The settings template allows `git grep *` without a prompt, and `git grep -O<command>` (or `--open-files-in-pager`) runs the command as a pager on the matching files, so a prompt injected from a fetched page could run any command. The guard hook (`guard-commands.sh`) now blocks the flag in every spelling git accepts: `-O` alone or with its command attached (`-Ovim`), inside a cluster of short options (`-iO`, `-nOvim`), quoted, after git's own `-C <dir>` or another command, and `--open-files-in-pager` shortened to any prefix from `--op`. A `-O` that is the value of `-e`, `-f`, `-A`, `-B`, `-C` or `-m` (`git grep -e -O`), and one named in a pattern or after `--`, pass. `settings.json` also denies the plain forms (`Bash(git grep *--open*)` and `Bash(git grep *-O*)`). Nothing denied the places where a credential sits, so `settings.json` now denies the Read tool `~/.ssh`, git's credentials files (`~/.git-credentials` and `~/.config/git/credentials`) and the gh CLI's token store (`~/.config/gh`, and `GitHub CLI` under `AppData/Roaming` on Windows). The guard blocks a shell `cat`, `head`, `tail`, `less`, `more` or `strings` of them however the path is written (`~/`, `$HOME/`, `${HOME}/`, `/c/Users/<name>/`, `C:\Users\<name>\` or relative), and the commands that print a stored credential: `gh auth token`, `gh auth status -t` (or `--show-token`) and `git credential fill` or `get`. A commit message that names them isn't blocked. Last, the pre-commit hook ran the check, and the secrets rule with it, only when a commit staged something other than Markdown outside `adr/`, so a token pasted into a page went into history unscanned. It now scans for secrets on every commit, whatever is staged, with the new `bash tools/check.sh --secrets`: the check's patterns, `[scan] skip` folders, emulator keys and ADR exceptions over the working tree, with no lock, printing only the file and line of each finding and never the secret. The whole check still runs only for a commit that stages more than documentation. `selftest.sh` feeds the hook each grep and credential case, fails when the template allows `git grep *` without its two deny rules or lacks any of the five Read rules, and commits a Markdown page that holds a secret in a throwaway repository and expects the hook to block it.
  - **Upgrade steps:** the hook, `tools/check.sh`, `.githooks/pre-commit` and `.claude/settings.json` are framework-owned and arrive with the upgrade (if you edited `.claude/settings.json`, merge its `.satt-new` file). Restart Claude Code so the new deny rules load. A commit that stages only Markdown is now scanned too: if the scan flags a page that holds an example, change the example to a placeholder such as `<from Key Vault>`, or record an accepted ADR with `- Exception: secrets <path>`.

## 0.14.2 (2026-10-30)

- **The guard blocks the git flags that write a file, read any file or run a configured command.** The settings template allows `git diff *`, `git log *`, `git show *` and `git commit *` without a prompt, and each takes any flag after it. `--output=<path>` writes a file to any path, such as one a later command runs; `--no-index`, a `git diff` of a path outside the repository, and `git commit -F <path>` or `--file <path>` read any file on the machine; and `--ext-diff` runs an external command from the git configuration. A prompt injected from a fetched page could use them to read a credential or plant a script, so the guard hook (`guard-commands.sh`) now blocks each flag, whether it is quoted (`'--output=x'`), escaped (`--out\put=x`), attached to a short option (`-aF`) or follows another command, and it doesn't block a flag named inside a commit message or a heredoc body. `settings.json` also denies the plain forms (`Bash(git *--output*)`, `Bash(git *--no-index*)`, `Bash(git *--ext-diff*)` and `Bash(git commit *--file*)`), which the harness enforces itself. A commit message is given with `-m`, or on stdin with `git commit -F -` (`--file=-`), which the guard passes. `selftest.sh` feeds the hook each case, and fails when the template allows a wildcard git rule without all four deny rules.
  - **Upgrade steps:** the hook and `.claude/settings.json` are framework-owned and arrive with the upgrade (if you edited `.claude/settings.json`, merge its `.satt-new` file). Restart Claude Code so the new deny rules load. A commit message that came from a file (`git commit -F message.txt`) now comes from stdin (`git commit -F - <<'EOF'`) or `-m`.

## 0.13.0 (2026-10-25)

- **A recurring security assessment validates what is built against the OWASP baseline.** The baseline was stated and reviewed per change, but nothing checked the whole app against it. A new `/security` skill runs `procedures/security.md` with the checklist in a new `reference/owasp.md`: each OWASP Top 10 category (named as its baseline row in `compliance/mapping.md`) and each API Security Top 10 category (under the row it belongs to) broken into checks a reader can verify, paraphrased from OWASP ASVS 5.0 level 1 by chapter, each marked `code`, `config` or `people` and pointing at where to look in this architecture (the host's token validation, tenant scoping in the stores, Key Vault and managed identities, Service Bus consumers, the web client, Bicep), plus which OWASP item each tool covers, what a clean run doesn't prove, and a severity rubric (a tenant isolation break is always high). The procedure runs the tools first, each skipped with a note when it isn't installed and never installed without asking: the check's `secrets`, `tenant-source`, `tenant-branching` and `network-public` rules, `dotnet list package --vulnerable --include-transitive` on the configured target or the solution found (a `.sln` first), `npm audit --omit=dev` with Corepack kept offline and never prompting, `pip-audit --disable-pip --no-deps` only on requirements pinned with `==` (it never installs them), Semgrep with `p/owasp-top-ten` keeping only path, line, column and rule (never the matched source, so a secret isn't copied), and the shipped workflow's last dependency review and SBOM through `gh`. Then a read-only reviewer in a fresh context goes category by category, reads the code each check concerns and cites file and line. Each finding (OWASP item, severity, evidence, proposed fix) becomes a bug item, high first; people and process work (access reviews, incident response, alert routing and on-call, key rotation, the security officer's sign-off) goes to the director as a list, and becomes `human` items only where the director agrees. The report goes to `assessment/security/YYYY-MM-DD.md` with the date, the commit, what ran, what was skipped and why, and a line per category: verified, findings, not checkable here, or not applicable. A tool passing never marks a category met. The assessment updates Met by, Label and Evidence of the OWASP rows in `compliance/mapping.md` (never `direct` from a tool alone) and names the rows of the customer's own framework a finding touches. `release.md` runs it before a release is proposed when something was built since the last report or none exists, and whether or not it runs, an open high bug naming an OWASP item blocks the release unless an accepted ADR deviates from that item. `next-task.md` proposes it when no report exists yet, or once `tools/check.cfg` › `[security] every` items (default 10) are done since the last report, counting squash-merge subjects such as `feat: x (T12) (#34)` and noting that a shallow clone may count low; the human can decline, and a run of several items carries on and only names it. A fixture in `tests/security/` has a vulnerable app (a key in config, the tenant from a header, a public Service Bus, vulnerable NuGet and npm packages, an injection, a delete without authorization) and its clean twin; the self-test proves the check's rules fire on the first and not the second, runs `npm audit` and `dotnet list package --vulnerable` where they are installed and online, and checks the wiring. Its manifests carry `.fixture` names so GitHub's dependency graph doesn't read them, and the self-test renames them in its copy. A tool counts as clean only when it exits 0 with its nothing-found summary; a timeout, a network or restore error or a Semgrep error is "couldn't run". Semgrep's output stays in `.satt/state/` and only `path:line:col:rule` is ever printed, and no report or bug item quotes a secret, only its `file:line` and kind. `tests/security/README.md` holds the manual acceptance check for the reviewer's findings.

## 0.12.0 (2026-10-25)

- **The shipped workflow reviews dependency changes and exports an SBOM.** `.satt/templates/check-workflow.yml` has two more jobs beside the check. `dependency-review` runs on pull requests with `actions/dependency-review-action@v4` and fails one that adds a dependency with a high or critical advisory (`fail-on-severity: high`, with the reason in a comment); it needs the dependency graph on for the repository. `sbom` runs on each push to main, exports the dependency graph from `GET /repos/{owner}/{repo}/dependency-graph/sbom` with `gh api` and the job's token, checks that the answer is an SPDX document, and keeps `sbom.spdx.json` as the artifact `sbom-<run number>-<attempt>`, with no `retention-days`. Both jobs have read-only permissions. `reference/infra.md` has a section, Dependencies and the SBOM, that says what the two jobs cover, what they don't (code, container images, Azure resources, transitive dependencies the graph can't see), and that vulnerability response stays the customer's process. The self-test checks both jobs' triggers, commands and upload, and the section.
  - **Upgrade steps:** apps that installed the workflow copy the `dependency-review` and `sbom` jobs from the source's `.satt/templates/check-workflow.yml` into their `.github/workflows/check.yml`, keeping their own stack steps. Turn on the repository's dependency graph first (private repositories need GitHub Advanced Security), or leave the `dependency-review` job out. Onboarding's offer installs the whole template for apps that don't have the workflow yet.
- **A compliance mapping table that review and align read.** Requirements sat in `compliance/`, but nothing tied a control to the rule, ADR or test that meets it. The seed `project/compliance/mapping.md` is a table with Control, Requirement, Met by (a rule id, `ADR-NNNN`, a test path or `none yet`), Label (`direct`, `partial`, `interpretive` or `unverified`, as `research.md` uses them) and Evidence (where an auditor finds it), with one example row to delete. Its header says a row is a claim a reviewer checks, that evidence of operation comes from the running system, and that a framework's name never marks a control met. `architect.md` adds or updates a row when an accepted ADR meets or deviates from a requirement, and never adds a `direct` row without naming what meets it. `review.md` flags a row as possibly stale (a finding, not a block) when the diff changes a rule in `archcheck.awk`, an ADR or a test that a row names. `align.md` reports rows whose rule, ADR or test no longer exists and `direct` rows whose Met by is `none yet`. The self-test checks the seed, the four procedures and onboarding.
  - **Upgrade steps:** onboarding offers the table once, when `compliance/mapping.md` is absent: copy the source's `project/compliance/mapping.md`, which starts empty apart from the example row. An existing file is never overwritten, and nothing else changes.
- **A shipped CI workflow keeps the check's output as evidence.** The check runs on the developer's machine and its logs sit in the gitignored `.satt/state/`, so a passing check left no record elsewhere. `.satt/templates/check-workflow.yml` is a GitHub Actions workflow that runs `bash tools/check.sh` on every pull request and every push to main with `permissions: contents: read`, sets up .NET, Node.js and Python where the app has their files, restores dependencies with `tools/setup-clone.sh --skip-hook`, and uploads the check's output and logs (without `secrets.txt`) as the artifact `check-<run number>-<attempt>` with `if: always()`. A failed check (exit 1) and one that couldn't run (exit 3) both fail the job. It sets no `retention-days`, so the repository's or organisation's Actions setting decides how long it is kept. Onboarding offers to copy it to `.github/workflows/check.yml` for new and existing apps, never overwrites an existing file, and `procedures/release.md` names the CI run and its artifact as where the check's result for the release commit lives. The self-test checks the template's triggers, permissions, steps and upload.
  - **Upgrade steps:** onboarding offers the workflow once: copy `.satt/templates/check-workflow.yml` to `.github/workflows/check.yml`, delete the stack steps the app doesn't use and set the toolchain versions. Nothing changes unless the human accepts, and an existing `.github/workflows/check.yml` is left as it is.
- **The check fails Bicep that leaves public network access or local authentication on.** A new `network-public` rule reads each Bicep resource of a type the reference architecture uses and Azure has the setting for, and fails when the property is missing or not the safe value: Cosmos DB accounts and Key Vaults need `publicNetworkAccess: 'Disabled'`, Cosmos DB and Service Bus need `disableLocalAuth: true`, and Storage accounts need `publicNetworkAccess: 'Disabled'` and `allowSharedKeyAccess: false`. Service Bus Standard, the default, has no private endpoints, so it is held to local authentication off only; a Premium namespace must also disable public access. An accepted ADR with `Exception: network-public <path>` excuses a file. A new `reference/network.md` gives the default posture, where it applies, what the check does and doesn't enforce (egress control, network security groups and Azure Policy stay with the customer's platform) and the ADR path; `cost.md` says private-only Service Bus needs Premium, so an ADR with a `cost-sku` exception. The rule is switched by `tools/check.cfg` › `[rules] network-public`: on in the seed for new apps, and off when the key is absent, so an upgraded app isn't failed until it turns it on. The self-test seeds a fault for each covered type, the compliant and excused cases, and the off and absent settings.
  - **Upgrade steps:** `tools/check.cfg` is project-owned and kept, so the rule stays off. To turn it on, add the `[rules]` section from the source's `project/tools/check.cfg` (`network-public = on`), then give every covered resource in the app's Bicep the properties above, or record an ADR with `Exception: network-public <path to the Bicep file>` (and `cost-sku` for a Premium namespace). The reference, procedures and check are framework-owned and arrive on upgrade.
- **The repository's own TASKS.md has one queue and unique IDs.** It had three Queue headings and two items numbered T9; the second is now T17. This changes nothing in an installed app.
  - **Upgrade steps:** none.
- **The README says a claim protects only its own worktree.** The parallel-sessions note now matches `rules.md`: sessions that build at the same time each take a git worktree, and an `in-progress` claim in TASKS.md protects only its own worktree.
  - **Upgrade steps:** none.
- **The command guard blocks commands that hang, and the check limits its test runs.** Across real projects, commands hung for minutes or forever, and any command past five minutes lets the prompt cache expire, so the next turn rewrites the whole context. `.claude/hooks/guard-commands.sh` (now also run for Monitor) blocks, each time with a message that gives the form that works: Python (`python`, `python3`, `py`, with or without `.exe`) reading `-` from a heredoc whose body is empty, the "is Python here?" probe that waits for console input on Windows and never returns (use `python3 --version`); an `until` or `while` loop with `sleep` that isn't under `timeout` with 280 seconds or less (`timeout 240`, `timeout 4m`); a loop that reads a background command's `tasks/<id>.output` without waiting for its `[exited with code N]` or `[killed]` line; and a lone `sleep` over 280 seconds. A non-empty Python heredoc, a loop under `timeout 240`, the end-marker loop and a short sleep pass. The guard still starts no other process. `rules.md` says, in Doing the work: give every long command a limit under five minutes, start a long check with `run_in_background` and wait for its completion notice, and never probe with an empty heredoc. `tools/check.sh` runs each test command (`dotnet test`, `npm run test`, pytest or unittest, and `tools/check.local.sh`) under GNU `timeout` when it is available, for `[tests] timeout` seconds in `tools/check.cfg` (default 600, or `CHECK_TIMEOUT`); a run that hits the limit exits 3 and says so, instead of reading as a pass or a test failure, unless a test had already failed. The self-test covers every block, every allowed form and the check's limit.
  - **Upgrade steps:** `tools/check.cfg` is project-owned and kept; add the `[tests]` section from the source's `project/tools/check.cfg` (`timeout = 600`) if you want a limit other than the default. Without it the default applies. The hook, rules, check and settings are framework-owned and arrive on upgrade.

- `architect.md` gives effort on a scale (S, M, L, or person-days for anything bigger), and `reference/cost.md` prices a web front end (Static Web Apps Free), so every client option in `clients.md` has a cost.

## 0.1.0 (2026-10-01)

The first version: a workflow for building a B2B SaaS from scratch, or turning a proof of concept or an existing app into a mature multi-tenant SaaS on Azure, with an architecture the framework owns and enforces.

### Authority
- **The human owns the product; the framework owns the architecture; the AI builds.** The reference architecture is `.satt/reference/`, one topic per file: layers, tenancy, identity, messaging, data, API, clients, integrations, infrastructure, cost, observability, stacks.
- **Deviations are ADRs the human accepts** (`adr/`, procedure `architect.md`). The check accepts a violation only when an accepted ADR names it in an `Exception:` line; proposed ADRs excuse nothing, exceptions for every path are refused, and stale exceptions are reported.
- **A Claude Code authority hook** asks the human before the assistant edits a framework-owned file or writes `Status: accepted` into an ADR.

### The check
- **`tools/archcheck.awk`**, portable awk, enforces the rules `layers`, `domain-purity`, `tenant-source`, `tenant-branching`, `secrets`, `file-size`, `host-size`, `message-version` and `cost-sku`, for C#, VB.NET, F#, TypeScript and JavaScript, Python, Java and Kotlin, Dart, Swift, .NET project files and Bicep. `bash tools/check.sh --architecture` runs it alone in seconds, with no toolchain.
- **Stack profiles** in `tools/stacks/`: `dotnet` (the default), `typescript`, `python`, and `none` (builds and tests from `tools/check.local.sh`).
- Bicep compiles when the CLI is installed. The check never calls Azure or an external system.

### Workflow
- Procedures: `next-task`, `build`, `review`, `roadmap` (the stages of the move to SaaS: extract, foundation, tenancy and identity, first slice, delivery, clients, integrations, second tenant, capabilities), `product`, `architect`, `integrate` (Navision / Business Central first), `tenant`, `acceptance`, `feedback`, `release`, `align`, `prune`.
- Onboarding settles the backend stack with the human: on an existing app it asks for a preference, keeps a compatible stack, and lists the compatible ones otherwise. It records the choice as ADR-1.
- Records: `product/prd.md`, `product/decisions.md`, `adr/`, `integrations/<system>/contract.md`, `TASKS.md` with `(test)`, `(check)` and `(demo)` outcomes, `validation/` for acceptance checks and feedback.
- The command guard also blocks deleting Azure resources, complete-mode deployments, reading Key Vault secrets and creating client secrets.

### Install
- As a Claude Code plugin (`/plugin marketplace add Freakling/SaaSAllTheThings`, then `/saasallthethings:saas-all-the-things`), with the skills CLI (`npx skills add Freakling/SaaSAllTheThings`), or by hand. The skill is self-contained: outside the plugin it clones this release (`v0.1.0`) into a temporary folder and follows `ONBOARDING.md` from there.
